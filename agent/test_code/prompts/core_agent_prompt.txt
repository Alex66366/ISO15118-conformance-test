**HARD CONSTRAINT (NON-NEGOTIABLE) — FOR EVERY TC YOU GENERATE:**

## CRITICAL: Session ID Persistence (Sprint 3.3 rewrite)

> **Update 2026-07-14 / Sprint 3.3:** The previous version of this section
> instructed the LLM to call `setparameter("session_id", ...)`.  After
> running the TITAN compiler on the LLM's output we discovered that
> **`setparameter` is NOT a TTCN-3 built-in** — it's a method that must
> be defined on a specific test port.  Our V2G port does NOT define it.
> Calls to `setparameter(...)` therefore fail with `There is no local or
> imported definition with name 'setparameter'`.  This rule rewrite
> replaces the `setparameter` API with the framework's actual mechanism
> for session-ID persistence: **embed `vc_SessionID` in the JSON
> envelope's `Header.SessionID` field of every subsequent request**.

ISO 15118-2 is a stateful multi-message protocol. SessionSetup returns a
new `SessionID`; every later request MUST carry that exact `SessionID` in
its JSON envelope. **Static hard-coded `"0000000000000000"` is a bug
after SessionSetup.**

### Pattern — extract and persist the SessionID inside a PR

```ttcn3
// 1. After receiving the SECC response (inside the receive-raw branch):
var octetstring resp_payload := v_msg.raw;
var charstring  resp_json    := oct2char(resp_payload);

// 2. Validate ResponseCode via match() (the ONLY safe TTCN-3
//    substring-detection API — see HARD RULE #3).
var boolean resp_ok := false;
if (match(resp_json, "*\"ResponseCode\":\"OK*\"")) {
    resp_ok := true;
}

// 3. Extract the 16-hex-char SessionID from the canonical envelope.
//    The value sits at offset 33 (after {"V2G_Message":{"Header":{"SessionID":")
//    and runs for 16 chars.
if (resp_ok and match(resp_json, "*\"SessionID\":\"*\"*\"")) {
    vc_SessionID := char2oct(substr(resp_json, 33, 16));
}

setverdict(pass, "SessionSetup exchange completed");
```

### Pattern — pass vc_SessionID into a downstream PR/TB

The cleanest way to share `vc_SessionID` between PRs is to:

1. Declare `vc_SessionID` as a **component variable** in the component
   type definition (the component owns its lifecycle, NOT the module —
   see SPRINT 3.3 fix below for the failure mode).
2. Embed `vc_SessionID` in the JSON `Header.SessionID` of every
   downstream request, using charstring concatenation (`&`).

```ttcn3
// Downstream PR / TB — embed vc_SessionID in the JSON envelope:
var charstring json_req :=
    "{"
    & "\"V2G_Message\":{"
    & "\"Header\":{\"SessionID\":\"" & oct2char(vc_SessionID) & "\"},"
    & "\"Body\":{"
    & "<message_type>:{...}"
    & "}"
    & "}"
    & "}";

pt_V2G_TCP_TLS_ALM_SECC_Port.send(char2oct(json_req));
```

### Where vc_SessionID lives (Sprint 3.3 architectural fix)

TTCN-3 has **no global variables** (verified against the ETSI standard
and the TITAN compiler). The Sprint 3.2 prompt's `var charstring
vc_SessionID := "..."` declared at module scope was rejected by TITAN
with `syntax error, unexpected VarKeyword`.

The legal place for `vc_SessionID` is in the **component type**
definition:

```ttcn3
// In SECC_TestSystem.ttcn (the component type module):
type component SECCTester {
    port V2G_TCP_TLS_Port pt_V2G_TCP_TLS_ALM_SECC_Port;
    port V2G_UDP_SDP_Port pt_V2G_UDP_SDP_Port;

    // Sprint 3.3: SessionID lives on the COMPONENT, not in the module.
    var octetstring vc_SessionID := '0000000000000000'O;
}
```

When a PR function needs to **return** the negotiated SessionID back to
the caller (TC orchestrator), it should expose it via an `out` parameter:

```ttcn3
function f_SECC_CMN_PR_SessionSetup_001(
    out octetstring po_session_id
) runs on SECCTester return verdicttype {
    // ...
    po_session_id := vc_SessionID;
    // ...
}
```

The TC orchestrator then stores the result on its own component
variable, where the downstream PRs can read it.

### Key rules (Sprint 3.3)

- **`setparameter` is NOT a TTCN-3 built-in.** Never emit it. Use the
  JSON-envelope embedding pattern above instead.
- **`var charstring` at module scope is illegal.** Use component-scope
  variables, or `out` parameters.
- **`match()` with `*` wildcards is the only safe substring-detection
  API that compiles in TITAN.** `regexp(...) != -1` and `indexof(...)`
  are both illegal.
- **`vc_SessionID` MUST be exactly 16 hex chars** (XSD contract: 8 bytes
  for V2G SessionID).  Placeholders like `"AUTO"` or `"SESSION_01"`
  must never appear.
- Every request after SessionSetup MUST embed `vc_SessionID` in the
  JSON `Header.SessionID` field — static `"0000000000000000"` is a bug.

### Common mistake to avoid

```ttcn3
// WRONG — calling setparameter (does not compile):
setparameter("session_id", oct2char(vc_SessionID));

// WRONG — module-scope var (does not compile):
module f_PR_SessionSetup {
    var charstring vc_SessionID := "0000000000000000";  // ILLEGAL
    // ...
}

// CORRECT — embed SessionID in the JSON envelope of every downstream
// request, using vc_SessionID from the COMPONENT scope (declared in
// SECC_TestSystem.ttcn):
var charstring json_req :=
    "{"
    & "\"V2G_Message\":{"
    & "\"Header\":{\"SessionID\":\"" & oct2char(vc_SessionID) & "\"},"
    & "\"Body\":{"
    & "\"ServiceDiscoveryReq\":{}"
    & "}"
    & "}";
```

| `urn:iso:std:iso:15118:-20:CommonMessages` | ISO 15118-20 common |
| `urn:iso:std:iso:15118:-20:AC` | ISO 15118-20 AC |
| `urn:iso:std:iso:15118:-20:DC` | ISO 15118-20 DC |
| `urn:iso:std:iso:15118:-20:WPT` | ISO 15118-20 WPT |
| `urn:iso:std:iso:15118:-20:ACDP` | ISO 15118-20 ACDP |

**`urn:iso:15118:2:2010:MsgDef` does NOT exist** — this is the most common LLM hallucination.
Unknown namespace → `getSchema()` returns null → silent NPE.

### RULE 2 — PascalCase JSON Keys (Silent field drop if violated)

MOXy uses the **XSD element name** as the JSON key, NOT the Java field name.
Java fields are camelCase, but `@XmlElement(name="AppProtocol")` rewrites them to PascalCase.

- WRONG: `{"appProtocol": [{"protocolNamespace": "..."}]}`
- RIGHT: `{"AppProtocol": [{"ProtocolNamespace": "..."}]}`

If a key is wrong, MOXy **silently drops the field** with no exception. ENCODE returns a 2-byte
empty EXI. There is no error to catch. Verify by checking EXI byte count.

**Common LLM mistakes — always use the right column:**
| LLM writes (wrong) | Must be (PascalCase) |
|---|---|
| `evccID`, `evccid` | `EVCCID` |
| `sessionID`, `sessionId` | `SessionID` |
| `paymentServiceSelectionReq` | `PaymentServiceSelectionReq` |
| `serviceDiscoveryReq` | `ServiceDiscoveryReq` |
| `chargeParameterDiscoveryReq` | `ChargeParameterDiscoveryReq` |
| `powerDeliveryReq` | `PowerDeliveryReq` |
| `authorizationReq` | `AuthorizationReq` |
| `cableCheckReq` | `CableCheckReq` |
| `preChargeReq` | `PreChargeReq` |
| `currentDemandReq` | `CurrentDemandReq` |
| `meteringReceiptReq` | `MeteringReceiptReq` |
| `protocolNamespace` | `ProtocolNamespace` |
| `versionNumberMajor` | `VersionNumberMajor` |
| `schemaID` | `SchemaID` |

The pipeline now auto-corrects camelCase keys (see `sanitize_v2g_json_keys`), but
writing them correctly the first time saves a sanitizer round-trip and prevents
misleading pipeline logs.

### RULE 3 — hexBinary = Hex String (Not base64, Not "AUTO")

SessionID (8 bytes), EVCCID (6 bytes), GenChallenge (16 bytes), OEMProvisioningCert, and
all other XSD `hexBinary` fields must be HEX-encoded strings, not base64.

- WRONG: `"EVCCID": "q83vASNF"`   (base64)
- WRONG: `"SessionID": "AUTO"`     (placeholder string)
- WRONG: `"SessionID": "SESSION_01"` (placeholder string)
- RIGHT: `"EVCCID": "ABCDEF012345"`   (hex, 12 chars = 6 bytes)
- RIGHT: `"SessionID": "0000000000000000"` (hex, 16 chars = 8 bytes, zero-init)

MOXy validates with regex `[0-9a-fA-f]+` and rejects base64 with `contains illegal character for hexBinary`.
The word "AUTO" or any non-hex string in a hexBinary field causes `contains illegal character for hexBinary`.

For SessionID, always use `"0000000000000000"` for an initial/established session,
or the actual session ID from a previous response. Never use placeholder strings.

### RULE 3.5 — Single-String JSON Literals Only (NO `&`-Concatenated Multi-Line Builds)

The TTCN-3 tokenizer treats each `"..."` literal as a self-contained string. When the LLM
builds a JSON payload via `&`-concatenation across multiple lines, brace-balance is **off by
one almost every time** (missing 2–3 closing `}`), and the TITAN compiler **still accepts
the source** because all `"..."` pieces are individually valid string literals. The bug
surfaces only at EXI encode time:

```
org.json.JSONException: Expected a ',' or '}' at 111 [character 112 line 1]
```

Root cause (real bug, TC_SECC_AC_VTB_ServiceDiscovery_001, 2026-07-13): Core Agent
hand-built the SessionSetupReq payload as 6 separate `"..."` chunks joined with `&`,
resulting in a JSON literal with 8 `{` and only 5 `}`. The compiler said "OK", the
EXI microservice said "broken JSON", and the runtime loop never got a chance to fix it
because `_runtime_self_repair` crashed on a separate NameError (`pcap_output=pcap_output`).

**HARD RULE — DO NOT VIOLATE:** Whenever you need to send a V2G body message as JSON
via `pt_V2G_TCP_TLS_ALM_SECC_Port.send(char2oct(X))`, the `var charstring X := ...`
declaration MUST be a **single one-line `"..."` literal**. Multi-line `&`-concatenation
of `"..."` pieces is **FORBIDDEN**.

- ✅ CORRECT (single one-line literal):
  ```
  var charstring ss_req_json := "{\"V2G_Message\":{\"Header\":{\"SessionID\":\"0000000000000000\"},\"Body\":{\"SessionSetupReq\":{\"EVCCID\":\"020000000001\"}}}}";
  pt_V2G_TCP_TLS_ALM_SECC_Port.send(char2oct(ss_req_json));
  ```

- ❌ WRONG (multi-line `&`-concatenation — produces unbalanceable JSON):
  ```
  var charstring ss_req_json :=
      "{"
      & "\"V2G_Message\":"
      & "{\"Header\":{\"SessionID\":\"0000000000000000\"},"
      & "\"Body\":{\"SessionSetupReq\":"
      & "{\"EVCCID\":\"020000000001\"}}"
      & "}";   // ← braces off by one
  ```

The pipeline's `sanitize_json_concat_literal` post-processor **will** rewrite your
multi-line concat to a canonical single-line literal — but at the cost of an extra
runtime-loop iteration and one or two watchdog hits. Save yourself the trip: write
the JSON as one literal, exactly as shown in the Canonical Correct Examples below
(RULE 4). If you need to embed a runtime-computed value (e.g. a SessionID returned
from a previous message), use TTCN `&` AFTER `oct2char()` of an `octetstring`, NOT
across multiple `"..."` literals.

### RULE 4 — V2G_Message Structure

V2G_Message body uses ObjectFactory `@XmlElementDecl` names. Top wrapper is always PascalCase.

```json
{"V2G_Message": {
    "Header": {"SessionID": "0000000000000000"},
    "Body": {"SessionSetupReq": {"EVCCID": "020000000001"}}
}}
```

When generating TTCN-3 templates that produce JSON payloads, always verify the JSON against

### HARD RULE #3 — JSON RESPONSE PARSING: USE `match()` + `substr()` (THE ONLY TTCN-3 STRINGS API THAT COMPILES)

**Update 2026-07-14 / Sprint 3.3 — IMPORTANT CORRECTION.**

The previous version of this rule banned `match()` and asked the LLM to use
`regexp()` and `indexof()`. **That was wrong.** Those function names do not
exist in the TTCN-3 BNF the way they were used:

  * `regexp(<str>, pattern(...), <group>)` in TITAN returns a **substring**
    matched by the regex (you must put `(...)` capture groups inside the
    pattern); it does NOT return `-1` on mismatch — it raises a runtime
    error. The `regexp(...) != -1` idiom is illegal TTCN-3.
  * `indexof(charstring, charstring)` is **not a TTCN-3 / TITAN function at
    all**. The compiler rejects it with `unexpected '('`. There is no
    `indexof` for charstrings — only `substr(...)` and `replace(...)`.

Therefore the LLM-generated PR / TB that followed the previous prompt
compiled with errors like:

    f_SECC_CMN_PR_SessionSetup_001.ttcn:43.46: error: at or before token `(':
        syntax error, unexpected '(', expecting Identifier or Cstring

The only safe, compile-clean way to parse JSON substrings in TTCN-3 is the
**string-pattern `match()`** function (with `*` wildcards) plus `substr()`
for slicing. Use these — no exceptions.

**Option A — `match()` for ResponseCode / field presence checks (preferred):**

```ttcn3
var boolean resp_ok := false;
if (match(resp_json, "*\"ResponseCode\":\"OK*\"*")) {
    resp_ok := true;
} else if (match(resp_json, "*\"ResponseCode\":\"FAILED*\"*")) {
    setverdict(fail, "<msg> rejected by SECC: ResponseCode=FAILED_*");
} else if (match(resp_json, "*\"Notification\"*") or
           match(resp_json, "*ParsingError*")) {
    setverdict(fail, "<msg> Notification fault: ", resp_json);
} else {
    setverdict(fail, "<msg>: ResponseCode missing or unparseable: ", resp_json);
}
```

**Key TTCN-3 string-pattern facts** (so the LLM writes correct patterns):

  * `match(<charstring>, <charstring>)` returns `true` if the FIRST arg
    contains a substring matching the pattern in the SECOND arg.
  * The pattern syntax is: `*` is a wildcard for any sequence (including
    empty); other characters are literal. There is NO backslash escape —
    a literal `"` is just `"` inside the pattern literal.
  * The pattern is a `<charstring literal>`, so you embed it with double
    quotes just like any other string in TTCN-3.

**Option B — `substr()` for extracting a fixed-width field (SessionID, EVCCID):**

```ttcn3
// Substring extraction requires a known offset.  Walk the string
// character-by-character with a simple loop or, since SessionID is
// always 16 hex chars at a known relative offset after a known header
// key, use a small `match()`-then-`substr()` pattern:
//   1. match() to confirm the key is present
//   2. parse the offset manually with `replace()` or by counting
// For Sprint 3.3 we recommend extracting SessionID/EVCCID by:
//   - match() the surrounding JSON snippet, then
//   - walk the string with `for ... in [0..length-1]` and a state machine
// OR (simpler, sufficient for smoke tests): hard-code the index based on
// the canonical ISO 15118-2 envelope order:
//
//     {"V2G_Message":{"Header":{"SessionID":"<16 hex>"},"Body":...
//
// The `SessionID` value begins at the 33rd character of `resp_json`
// (after `{"V2G_Message":{"Header":{"SessionID":"`) and runs for 16 chars.
```

**Required JSON inspection checklist for TB / PR functions:**
- ResponseCode prefix (`OK_*` / `FAILED_*`) → `match(resp_json, "*\"ResponseCode\":\"OK*\"*")`
- Notification / FaultMsg presence → `match(resp_json, "*\"Notification\"*")`
- ParsingError presence → `match(resp_json, "*ParsingError*")`
- 16-hex-char SessionID extraction → either (a) character-by-character loop
  after a `match()` confirmation, or (b) hard-coded offset (see above).
- Any other field extraction → `match()` + `substr()` only. **No `regexp()`,
  no `indexof()`.**

**Self-check before submitting:** Search your generated code for any of
these illegal tokens and DELETE them:
  * `regexp(`
  * `indexof(`
If you find them on a `resp_json` / `json_req` / `v_msg.raw` argument,
you MUST rewrite them as `match(...)` + `substr(...)` before returning.

### HARD RULE #4 — PRECONDITION CHAIN MUST PROPAGATE DYNAMIC SESSION ID VIA `vc_SessionID`

ISO 15118-2 is a stateful multi-message protocol. SessionSetup returns a new `SessionID`; every later request MUST carry that exact `SessionID`. **Static hard-coded `"0000000000000000"` is a bug after SessionSetup.**

**Mandatory pattern — any PR that receives a `SessionID` from SECC:**

```ttcn3
// Inside the `receive({ raw := ? })` success branch, AFTER oct2char(...):
var charstring resp_json := oct2char(v_msg.raw);

// 1. Confirm the SessionID field is present and extract the 16-hex-char value.
//    (The value is always 16 hex chars at a fixed offset in the canonical envelope.)
if (match(resp_json, "*\"SessionID\":\"*\"*")) {
    // 2. Extract the 16-hex-char SessionID using match() + substr().
    //    The pattern matches "SessionID":"<16 hex>" and substr() pulls the value.
    //    The matched text is a 16-char substring starting 12 chars after '"SessionID":"'.
    vc_SessionID := substr(resp_json, 33, 16);
} else {
    // NOTE: Do NOT fallback to "0000000000000000" here — that causes the SECC
    // to reject follow-up requests with ValidationError ("Invalid value '' for SessionID"
    // because the SECC already established a real session.  Keeping the old vc_SessionID
    // value is the correct fallback; it preserves whatever SessionID was established
    // in an earlier PR (e.g. SupportedAppProtocol) and avoids the empty-string bug.
    log("WARN: SessionID field not found in response; keeping existing vc_SessionID");
}

// 3. Embed vc_SessionID in the JSON envelope of the NEXT send() call.
//    The C++ adapter does NOT persist SessionID between calls.
//    YOU must embed it explicitly in the charstring JSON payload.

// 4. Only then set verdict and return.
setverdict(pass, "SessionSetup exchange completed");
```

**Hard rules:**
- **NEVER** fallback to `"0000000000000000"` inside a PR/TB that has already received a real SessionID — doing so causes the SECC to crash with `Invalid value '' for SessionID`.
- **NEVER** use `setparameter("session_id", ...)` — this function does not exist in TTCN-3. The only way to pass SessionID to the SECC is to embed it in the JSON envelope: `& oct2char(vc_SessionID) &`.
- Every downstream send() in the same test case MUST embed `vc_SessionID` in the JSON `Header.SessionID` field. Static `"0000000000000000"` is forbidden after SessionSetup.
- If a later PR / TB needs the SessionID, it reads `vc_SessionID` from the component — it must not re-derive or hardcode it.

**Self-check before submitting:** Every precondition after SessionSetup that sends a `V2G_Message` MUST embed `vc_SessionID` into the JSON `Header.SessionID` field. If you are unsure whether a later function has access to `vc_SessionID`, assume it does and reference the variable.

## 🚨 HARD RULE (added 2026-07-14, mandatory for ALL TCs after Sprint 3.1) 🚨

**Every Test Behavior (TB) function MUST validate `ResponseCode` from the SECC response before setting `verdict(pass)`.**

### Why this rule exists
Recent batches (see `BATCH_ANALYSIS_20260714.md` §3) revealed that TBs were calling
`setverdict(pass)` after merely receiving *any* octetstring on `raw := ?`. The SECC
returns `FAILED_UnknownSession` with a Notification for malformed SessionIDs, but the
TTCN-3 receive branch ignored the response body content entirely. **Result: a TC was
declared "pass" while semantically the SECC had rejected the request.**

### Required pattern — copy this exactly when generating TBs

```ttcn3
[] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ raw := ? })
    -> value v_msg {
        tc_V2G_SECC_Msg_Timer.stop;
        var octetstring resp_payload := v_msg.raw;
        var charstring  resp_json    := oct2char(resp_payload);
        log("SECC <message_type> response (raw JSON): ", resp_json);

        // === ResponseCode validation (mandatory, see Sprint 3.1) ===
        // Parses the ResponseCode field from the JSON response.  We use
        // match() with the TTCN-3 string-pattern syntax (`*` wildcards;
        // no backslash escapes) — this is the ONLY substring-detection
        // method that compiles in TITAN.  See HARD RULE #3.
        var boolean resp_ok := false;
        if (match(resp_json, "*\"ResponseCode\":\"OK*\"*")) {
            resp_ok := true;
        } else if (match(resp_json, "*\"ResponseCode\":\"FAILED*\"*")) {
            // SECC explicitly rejected — surface the FailureCode for diagnosis.
            log("SECC rejected <message_type>: ", resp_json);
            setverdict(fail,
                "<message_type> rejected by SECC. ResponseCode=FAILED_*. "
                "See SECC log for ParsingError / Notification.FaultMsg.");
        } else if (match(resp_json, "*\"Notification\"*") or
                   match(resp_json, "*ParsingError*")) {
            // SECC rejected via Notification header (typical for SessionID mismatch).
            setverdict(fail, "<message_type> Notification fault: ", resp_json);
        } else {
            // Either OK with non-prefix ResponseCode, or unexpected body.
            // Be conservative — only PASS on OK prefix.
            setverdict(fail,
                "<message_type>: ResponseCode field missing or unparseable: ",
                resp_json);
        }
        if (resp_ok) {
            setverdict(pass,
                "<message_type> exchange successful — SECC returned OK ResponseCode");
        }
    }
```

### What NOT to do

```ttcn3
// ⛔ WRONG — sets pass on ANY received octetstring
[] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ raw := ? })
    -> value v_msg {
        setverdict(pass, "<message_type> exchange completed");
        // BUG: SECC may have returned FAILED_* or Notification, this still PASSes
    }
```

### Static lint check (post-generation)
The pipeline runs a static lint after generation. If the generated TB does NOT
contain a ResponseCode parse, the IA fix-loop is invoked and the LLM is asked to
patch the file. A successful patch MUST add:

1. A `match(resp_json, "*\"ResponseCode\":\"OK*\"*")` check
2. Distinct `setverdict(fail, ...)` calls for FAILED_* and Notification cases
3. A *separate* `setverdict(pass, ...)` guarded by an `if (resp_ok)` block

> **Sprint 3.3 update (2026-07-14):** the previous version of this rule asked
> for `regexp(...) != -1` and `indexof(...)` calls. Those do NOT compile in
> TTCN-3 / TITAN. The lint now enforces `match()` only, which is the only
> safe string-substring detection API in TITAN. See HARD RULE #3 for the
> full explanation.

If lint post-processing fails to add these, the build will FAIL with a clear
diagnostic: `[LINT] TB <module> missing mandatory ResponseCode validation`.

> **Sprint 3.2 update (2026-07-14):** the lint static patch has been
> re-written to emit a `match(...)` check instead of a `regexp(...)` check.
> `regexp()` and `indexof()` are not TTCN-3 / TITAN built-ins in the form
> previously used; auto-patches now use `match()` + `substr()` only.

This rule applies to ALL TB functions across ALL TC types. Sub-condition functions
(PR_*) are exempt because they only establish preconditions; the TB is where the
verdict is cast.
