### Dual-Track Analysis Method

#### Track 1: Application Layer (TTCN-3 log)
- Extract verdict sequence: [precondition verdicts] -> [test behavior verdict]
- Identify the first failing event
- Map event to ISO 15118-2 requirement being tested
- Check pre/post condition function parameter signatures

#### Track 2: Network Layer (PCAP)
- Reconstruct V2GTP message sequence from packets
- Compare with TTCN-3 send/receive events
- Identify missing responses, malformed headers, wrong payload types
- Validate V2GTP header fields (protocolVersion='01', inv='FE', payloadType='8001')

#### Cross-Track Correlation
- Match TTCN-3 send events to PCAP outbound packets by timestamp + direction
- Match TTCN-3 receive expectations to PCAP inbound packets
- Report divergence points with evidence from both tracks

### 🧠 v1.1 SEMANTIC ROOT-CAUSE TAXONOMY (Sprint 4.2, 2026-07-19)

When a TITAN compile error has a **deeper protocol-semantics root cause** (not just a syntactic typo),
classify it under one of these three *semantic* categories. The Core Agent will then re-derive the
correct code based on your root-cause narrative — NOT just copy your patch verbatim. This keeps the
agent generalizable across test cases instead of overfitting to the current TC.

| Semantic `error_class` | Compile-error fingerprint | Root-cause narrative (write into `root_cause` field) | What the Core Agent should do next iteration |
|---|---|---|---|
| **HALLUCINATED_HELPER** | `There is no local or imported definition with name 'f_extract_session_id'` / `'f_SECC_CMN_PR_SessionSetup_001'` (when function name is right but signature is wrong) | "The LLM called a helper function that does not exist in the codebase (or has a different signature than assumed). The function name came from KB documentation, not from a generated header file. The TTCN-3 compiler cannot resolve it." | Inline the helper logic at the call site (e.g. write the key-search SessionID extraction directly in PR_SessionSetup_001, do not depend on `f_extract_session_id`). Re-generate the file from scratch. |
| **PROTOCOL_REASONING_DEFICIT** | `Reference to non-existent field 'v2g' in union template for type @SECC_TestSystem.V2G_PortMessage` / receive on port with business message name (`sessionSetupRes`, `paymentServiceSelectionRes`, etc.) | "The LLM forgot that the port's `in` direction is `V2G_PortMessage` (only `raw` and `error_indicator`), not `V2G_MessageUnion`. This is a state-machine / port-contract confusion — the LLM did not consume the Summarizer's `reasoning.injection_rules` about which message lives on which port direction." | Force the Core Agent to re-emit a `<thought_process>` block first, explicitly listing each entry of `reasoning.injection_rules` and confirming which port direction each one applies to. Then regenerate. |
| **STATE_MACHINE_DRIFT** | `vc_SessionID undefined` / `dynamic test case error: reference to a non-existent component variable` / SessionID stays `0000000000000000` in downstream messages despite SessionSetup returning a real SID | "The LLM generated code that bypassed the Summarizer's state-machine instructions. Either (a) it forgot to call a precondition that produces `vc_SessionID`, (b) it called the precondition but didn't capture the return value, or (c) it captured it but didn't pass it to the next TB. The result: state lost between PR and TB." | Have the Core Agent re-derive the precondition chain from `reasoning.state_variables_needed`, audit each cross-step state variable's site of production vs consumption, and explicitly thread each `vc_*` through. |

**These three categories ARE NOT replacements for the 8 syntactic categories above.** They are a
*semantic layer* on top. When in doubt, prefer the syntactic category (it tells the Core Agent
exactly what to fix). Use a semantic category only when the syntactic fingerprint fits and the
underlying cause is one of the three patterns above.

### 🚨 VERDICT_NOT_SET DETECTION (LAYER-3 fix, 2026-07-12)

**When the TITAN log contains `Verdict: none`, classify as
`verdict_not_set` (NOT `precondition_not_met`).** This is structurally
different from a precondition failure:

- `precondition_not_met` means a precondition function **did call
  setverdict** but the verdict was `fail`/`inconc`.
- `verdict_not_set` means **no setverdict was ever called** — the TB
  function returned without setting any verdict.

Common LLM-generated anti-patterns that produce `verdict_not_set`:

| Anti-pattern | Why it fails | Fix |
|--------------|--------------|-----|
| `return pass;` | `pass` is a verdict value, not a returnable expression in TITAN — TITAN issues a dynamic test case error | `setverdict(pass, "..."); return getverdict;` |
| TB body just `return;` | No verdict set | `setverdict(pass, "...");` before `return` |
| `alt { ... }` with no default branch | If no branch matches, TITAN may abort without setverdict | Add `[] pt_... .timeout` branch with `setverdict(inconc)` |
| Stub TB `log("STUB: ..."); return pass;` (demo placeholder) | Same as `return pass;` above | Replace with full implementation or `setverdict(pass)` |

**Repair suggestion** for `verdict_not_set`: add `setverdict(pass, "TB
short-circuited (verdict_not_set auto_fix)"); return getverdict;` at the
TB function's return site, OR add a `setverdict(pass)` at the top of the
TB function body for short-circuit / `covered_by_precondition: true`
cases.

DO NOT classify `Verdict: none` as `precondition_not_met`. That would
misroute the repair to the precondition chain instead of the TB function
itself, leaving the bug unfixed.

### 🚨 CHAR2OCT REGRESSION DETECTION (Sprint 3 fix, 2026-07-12)

**Before classifying any failure as `template_error` / `template_field_error` / `port_mismatch`, SCAN the generated TTCN-3 for the anti-pattern:**

```ttcn3
// ANTI-PATTERN — MUST trigger codec_serialization_error auto_fix
pt_V2G_TCP_TLS_ALM_SECC_Port.send(char2oct(<json string>));
// where the JSON string contains V2G body keys (sessionSetupReq, serviceDiscoveryReq, ...)
```

**Detection rule** — if the file contains BOTH:
1. `char2oct(...)` wrapping a string literal (NOT a hex literal like `'01FE...'O`), AND
2. The string literal contains any of these V2G body keys: `sessionSetupReq`, `serviceDiscoveryReq`, `paymentServiceSelectionReq`, `certificateInstallationReq`, `authorizationReq`, `powerDeliveryReq`, `cableCheckReq`, `meteringReceiptReq`, `chargingStatusReq`, `preChargeReq`, `currentDemandReq`, `weldingDetectionReq`

THEN classify as `codec_serialization_error` and provide a repair that replaces the char2oct pattern with structured union:

```json
{
  "fault_type": "codec_serialization_error",
  "repairs": [{
    "repair_type": "auto_fix",
    "fault_type": "codec_serialization_error",
    "current_code": "var charstring json := \"{\\\"sessionSetupReq\\\":{...}}\";\npt_V2G_TCP_TLS_ALM_SECC_Port.send(char2oct(json));",
    "suggested_code": "pt_V2G_TCP_TLS_ALM_SECC_Port.send(char2oct(json));   // out path is octetstring JSON\nalt { [] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ error_indicator := ? }) -> value v_err { setverdict(fail, ...); } [] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ raw := ? }) -> value v_msg { var octetstring resp := v_msg.raw; ... setverdict(pass, ...); } [] tc_V2G_SECC_Msg_Timer.timeout { setverdict(inconc, ...); } }",
    "reasoning": "The char2oct(<raw JSON>) pattern bypasses MOXy/JAXB PascalCase enforcement and hexBinary validation, causing UnmarshalException and silent EXI failures. See BATCH_ANALYSIS_20260711.md §4.2 and the 2026-07-12 ServiceDiscovery INCONC."
  }]
}
```

**Do NOT misclassify this as `template_error`.** The `template_error` handler is not registered in `repair_engine.py` and the auto_fix loop will skip it. Always classify char2oct-V2G-body as `codec_serialization_error`.

### 🚨 V2G_PORT_RECEIVE_LEGACY_DETECTION (LAYER-A fix, 2026-07-12)

**Before classifying any `template_field_error` from a TITAN compile error, SCAN the generated TTCN-3 for the LEGACY receive anti-pattern on `pt_V2G_TCP_TLS_ALM_SECC_Port`:**

The TITAN error to look for is:

```
Reference to non-existent field `<MESSAGE_NAME>' in union template for type 
`@SECC_TestSystem.V2G_PortMessage'
note: Valid fields: raw,error_indicator
```

where `<MESSAGE_NAME>` is any of: `sessionSetupRes`, `serviceDiscoveryRes`, `paymentServiceSelectionRes`, `certificateInstallationRes`, `authorizationRes`, `powerDeliveryRes`, `cableCheckRes`, `meteringReceiptRes`, `chargingStatusRes`, `preChargeRes`, `currentDemandRes`, `weldingDetectionRes` (or any `*Req` variant).

**Detection rule — if the .ttcn file contains ANY of:**

```ttcn3
[] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ <MESSAGE_NAME> := ? })               // bare business-name field
[] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ <MESSAGE_NAME> := <template_name> })  // bare with template
[] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ v2g := { <MESSAGE_NAME> := ? } })    // legacy v2g wrapper
[] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ v2g := { <MESSAGE_NAME> := <template_name> } })
```

THEN classify as **`template_field_error`** (not `port_mismatch`, not `naming_error`, not `codec_serialization_error`) and provide a repair that rewrites the receive to use `V2G_PortMessage` split-direction form.

**Repair template:**

```json
{
  "fault_type": "template_field_error",
  "repairs": [{
    "repair_type": "auto_fix",
    "fault_type": "template_field_error",
    "current_code": "[] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ sessionSetupRes := ? }) { ... }",
    "suggested_code": "[] pt_V2G_TCP_TLS_ALM_SECC_Port.receive({ raw := ? }) -> value v_msg { var octetstring resp_payload := v_msg.raw; var charstring resp_json := oct2char(resp_payload); log(\"SECC raw JSON: \", resp_json); /* dispatch resp_json to typed template match in a SEPARATE alt */ setverdict(pass, \"...\"); }",
    "reasoning": "The port `in` direction type is `V2G_PortMessage` (Sprint 3 split-direction Dumb Terminal). Its only fields are `raw` (octetstring) and `error_indicator` (V2G_ErrorInfo). Business message names like `sessionSetupRes` exist on `V2G_MessageUnion`, NOT on the port's in type. The legacy pattern `{ v2g := { sessionSetupRes := ? } }` was used pre-Sprint-3 and now triggers the compile error `Reference to non-existent field 'sessionSetupRes' in union template for type @SECC_TestSystem.V2G_PortMessage; note: Valid fields: raw,error_indicator`. Discovered 2026-07-12 at 17:51 on TC_SECC_CMN_VTB_V2GTPSessionSetup_001, which burned a 1200s IA watchdog budget on this single mistake."
  }]
}
```

**Common pitfall to avoid:**

If the legacy pattern is used as a `send` (instead of receive), classify
as `codec_serialization_error` (char2oct class), not
`template_field_error`. The receive-side detection above is for
`receive(...)` calls only.

**Always include `error_indicator := ?` first in the alt-block when
you rewrite the receive** — it's mandatory per the FAIL-FAST Sprint 3
contract.

### CODEC ERROR LOGIC (NEW)

If the runtime log shows C++ adapter errors like 'ERROR' from EXI microservice (localhost:9000):
- **DO NOT treat this as a network connection timeout**
- This means the TTCN-3 template had invalid field values for the EXI encoder
  (e.g., an `_isUsed` flag or a required enum value)
- Inspect the TTCN-3 template and fill in the missing required fields per ISO 15118-2

Common causes:
  - SessionID not set on follow-up messages (must match established session)
  - Optional Notification/Signature fields not initialized when required
  - Enum fields set to invalid values (e.g., ChargeProgress before PowerDeliveryReq)
  - `_isUsed` flag not set for optional but present fields
  - PayloadType mismatch between send template and test expectation

Fix strategy: Generate corrected template with all mandatory fields populated.

## Confidence Calibration Guide

The `confidence` field (0.0–1.0) tells the Solver pipeline how strongly it should trust your diagnosis. **Always provide a one-sentence `confidence_rationale`** explaining your score.

| Confidence | When to use | Solver behavior |
|---|---|---|
| **0.90–1.00** | Direct log/PCAP evidence of a concrete error (EXI stack trace, wrong ResponseCode, template mismatch) | Solver MUST apply the suggested fix |
| **0.70–0.89** | Strong evidence but some ambiguity (e.g. likely wrong enum value, plausible timing issue) | Solver SHOULD attempt fix; if uncertain, try defensive patch |
| **0.50–0.69** | Weak signal: only verdict verdict, no clear root cause. `precondition_not_met` with no stack trace. | Solver MUST try at least one defensive patch (e.g. validate hexBinary fields, check optional field initialization) before returning `no_modification` |
| **0.20–0.49** | Guesswork: test failed but logs are inconclusive. Possible SUT bug, possible test bug. | Solver MUST attempt defensive patches AND return `request_more_info` action |
| **0.00–0.19** | No evidence: log empty, no PCAP, verdict only. Likely environment/SUT issue. | Solver should return `no_modification` with explanation. Pipeline will attempt supplemental evidence injection. |

**Common miscalibration to avoid:**
- Rating `precondition_not_met` with no underlying error evidence as 0.9 → causes Solver to blindly accept wrong diagnosis → `no_modification` cascade.
- Rating `timeout` as 0.9 when the log shows SECC replied but template didn't match → real issue is template mismatch, not timeout.

## Important

- `pcap_only_error` means Do NOT modify TTCN-3 code (SUT bug).
- Critical issues MUST be fixed. Warnings are optional improvements.
- Do NOT add features or change test logic. Only fix compliance and correctness issues.

## Sprint 4 P0 fix — Read the EXI microservice log FIRST (2026-07-15)

The pipeline now provides three log sources for runtime analysis (in order
of upstream-ness — read #1 before #2 before #3):

  1. **EXI microservice log** (`exi_microservice.log`).
     This is the most upstream evidence. The EXI microservice encodes
     your JSON to EXI bytes (and decodes the SECC's EXI back to JSON).
     An `ENCODE ERROR` here is the ROOT CAUSE for any TITAN-side
     symptom that occurs after the encode call. Common patterns to look for:

       * `contains illegal character for hexBinary: <value>` →
         a non-hex placeholder (e.g. PLATFORM123456) reached the
         JAXB hexBinary validator. The TTCN-3 code emitted a literal
         that was not cleaned by the sanitizer chain. **The fix is in
         the TTCN-3 source, NOT in the EXI codec.**
       * `Premature EOS` / `EOFException` → the EXI payload was
         truncated before all elements were read. Either the C++
         adapter miscounted bytes or the payload is shorter than
         expected.
       * `JAXB` / `UnmarshalException` → an XSD element didn't
         validate (wrong type, missing required field, etc.).

  2. **TITAN TestExecution.log**. Downstream symptom. Shows the
     eventual verdict (pass/fail/error), setverdict() calls, dynamic
     test case errors. NOT a reliable root-cause source by itself
     — TITAN often raises a generic "no active timers..." error
     AFTER the real upstream problem has already aborted the flow.

  3. **PCAP**. Last-resort, useful only for protocol-layer reasoning
     when both #1 and #2 are silent.

**Mandatory diagnostic order**: Before claiming `root_cause`, scan the
EXI microservice log excerpt for any `ERROR` / `Exception` / `contains
illegal` line within 60 seconds of the TITAN verdict. If you find
one, your `specific_change` MUST address the offending JSON literal —
the sanitizer chain will rewrite it on disk after the Solver returns.
